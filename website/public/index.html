Why SQL stays messy

Valid isn't the same as correct

WHERE x = NULL runs without an error and matches no rows.

Style eats review time

Reviewers argue about commas and casing instead of the logic.

Team rules live in people's heads

"Marts read staging, not raw" holds until someone new misses it.

Autofixes you can't trust

A fix that changes which rows match is a bug, not a cleanup.

From a messy query to a clean one

Check, fix and format, then keep it that way with your own Rules, in CI and before every commit.

Find the problems

01 · Catch common mistakes

Flag SQL that runs but is easy to get wrong

Default Rules flag comparisons with NULL, NOT IN lists that contain NULL, and ROW_NUMBER with no deterministic order. Each finding points at the exact characters and says what to write instead.

How Rules work →

sqlclean check

  --> models/open_orders.sql:2:3

 2 |   ROW_NUMBER() OVER (PARTITION BY o.customer_id) AS order_rank
   |   ^^^^^^^^^^
  = help: Add ORDER BY with a stable tie-breaker inside the window specification.

error[SQC001]: Comparison with NULL is never true
  --> models/open_orders.sql:4:22
   |
 4 | WHERE o.cancelled_at = NULL
   |                      ^

  = fix: available with `sqlclean fix --unsafe-fixes`

error[SQC019]: NOT IN list contains NULL and can reject every row
  --> models/open_orders.sql:5:16
   |
 5 |   AND o.status NOT IN ('refunded', NULL)
   |                ^^^
  = help: Remove NULL from the list or express the anti-join with a NULL-safe NOT EXISTS.

02 · Fix safely

Apply safe fixes, and hold back the rest

sqlclean fix applies safe fixes until the file is stable, then formats it. A fix that can change which rows match, like = NULL to IS NULL, waits for --unsafe-fixes. A pass that would break parsing is thrown away.

How fixing works →

sqlclean fix --unsafe-fixes --diff
--- a/models/open_orders.sql
+++ b/models/open_orders.sql
@@ -1,5 +1,8 @@
-SELECT o.order_id, o.customer_id, o.total_cents,
-  ROW_NUMBER() OVER (PARTITION BY o.customer_id) AS order_rank
+SELECT
+    o.order_id,
+    o.customer_id,
+    o.total_cents,
+    ROW_NUMBER() OVER (PARTITION BY o.customer_id) AS order_rank
 FROM orders o
-WHERE o.cancelled_at = NULL
-  AND o.status NOT IN ('refunded', NULL)
+WHERE
+    o.cancelled_at IS NULL AND o.status NOT IN ('refunded', NULL)

03 · One canonical format

Stop arguing about layout

Every statement gets the same layout: upper-case keywords, one column per line and each clause on its own line. Formatting a formatted file changes nothing, and SQL the formatter can't lay out safely is reported and left as it is.

How formatting works →

sqlclean format --diff models/revenue.sql

Keep them fixed

04 · Make lessons permanent

Turn review comments into Rules

A custom Rule is a Python function over the tables, joins, columns and literals of each statement, already parsed and located for you. No regular expressions, no parser to learn. Here marts must read staging models, never raw tables.

Write a custom Rule →

# sql_rules/layers.py
@rule(
    code="XSQCLAYER001",
    message="Marts must not read raw tables",
    remediation="Read the staging model instead.",
    enabled_by_default=True,
)
def marts_read_staging(*, statement: Statement, ctx: RuleContext) -> list:
    if not statement.path.startswith("models/marts/"):
        return []
    return [
        ctx.finding(subject=statement, node=table)
        for table in statement.tables
        if table.qualified_name.startswith("raw.")
    ]

 5 | INNER JOIN raw.payments p
   |            ^^^^^^^^^^^^
  = help: Read the staging model instead.
05 · Test your Rules

Rules with tests, like any other code

sqlclean.testing parses each case with the same engine as sqlclean check and fails when the number of findings is wrong. It runs every case twice, in opposite file orders, to catch Rules that aren't deterministic.

Test a custom Rule →

# tests/test_layers.py
from sqlclean.testing import RuleCase, evaluate_rule

def test_marts_reading_raw_tables_are_reported() -> None:
    evaluate_rule(
        rule=marts_read_staging,
        test_case=RuleCase(
            description="a mart joins raw.payments",
            path="models/marts/revenue.sql",
            source="SELECT o.order_id FROM stg_orders o JOIN raw.payments p ON …",
            dialect="duckdb",
            expected_finding_count=1,
        ),
    )

06 · Review every exception

Allow a finding once, with a reason

An exception allows one Rule in one file, and for a cross join, one relation, with a reason a reviewer can read. When the SQL changes and the exception no longer matches, sqlclean check fails until it is removed, so allowances never outlive the code they covered.

How exceptions work →

# sqlclean.toml
[[rules.rule_exceptions]]
rule = "SQC038"
path = "models/marts/calendar.sql"
relation = "regions"
reason = "Every date is reported for every region."

sqlclean check

07 · Run it everywhere

Before every commit and in CI

Ready-made pre-commit hooks check, fix or format staged SQL. In CI, sqlclean check exits non-zero on findings and writes SARIF for code-scanning annotations, or JSON for anything else.

Set up CI and pre-commit →

# .pre-commit-config.yaml
repos:
  - repo: https://github.com/sqlstack-io/sqlclean
    rev: v0.0.1
    hooks:
      - id: sqlclean-fix
      - id: sqlclean-format
